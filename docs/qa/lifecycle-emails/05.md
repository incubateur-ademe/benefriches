## Setup and assumptions

The app is already running at `http://localhost:3001` (the e2e stack, `docker-compose.e2e.yml` + `.env.e2e`, from the repository root). It must have been **built from this branch after ticket 05 was implemented** (`make e2e-up-build`): the `api` image then contains the compiled daily job script, and the `api` container has the five new `LIFECYCLE_EMAILS_CONTACT_*` variables. No migration comes with this ticket.

Like 04, S15 **stops and starts the `mailcatcher` container** to simulate a mail outage (`dc stop mailcatcher` / `dc start mailcatcher`). MailCatcher keeps messages in memory, so the restart empties its inbox and restarts message ids at 1: run S9 (which reads the S1 message) before S15. The guide never restarts, rebuilds or stops the `api`, `web` or `postgres` containers. Always finish a scenario with MailCatcher back up.

Fixed facts about this running stack, taken from `.env.e2e` / `docker-compose.e2e.yml` and the plan (`.agents/tasks/lifecycle-emails/issues/05-first-site-reminder.plan.md`):

- Web app / API (proxied): `http://localhost:3001`. `POST /api/auth/register` registers a user (and sends the welcome email inline); the response sets the access-token cookie. `POST /api/sites/create-express` creates an express site; `POST /api/sites/:siteId/archive` (authenticated) archives it. `POST /api/lifecycle-emails/unsubscribe` (ticket 03) unsubscribes.
- MailCatcher UI/API: `http://localhost:1081`. The `api` container reaches it as `SMTP_HOST=mailcatcher`.
- Postgres: `postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db`. The volume persists across runs: the database already holds users from earlier e2e runs and QA sessions, some of them inside the 24–72 h window. S0 drains them.
- Inside the running `api` container: `LIFECYCLE_EMAILS_ENABLED=true`, `LIFECYCLE_EMAILS_UNSUBSCRIBE_SECRET=e2e-tests-unsubscribe-secret`, `WEBAPP_URL=http://localhost:3001`, and the fake contact from the plan (D5): `Mathilde` / `Lefèvre` / `Chargée de déploiement` / `01 23 45 67 89` / `mathilde.lefevre@example.com`.
- Daily job (plan D8): `apps/api/src/notifications/adapters/primary/sendDailyLifecycleReminders.script.ts`, compiled to `dist/src/notifications/adapters/primary/sendDailyLifecycleReminders.script.js`. One flag: `--dry-run`. For now it runs only `SendFirstSiteRemindersUseCase` (ticket 06 adds the first project reminder).
- Log lines (plan D8), the dry-run ones prefixed with `[DRY RUN] `:
  - window: `First site reminders: registered after <now − 72 h, ISO> and at or before <now − 24 h, ISO>`
  - dry run, one per user: `[DRY RUN] Eligible for first site reminder: userId=…, email=…, registeredAt=<ISO>`
  - contact missing (`warn`): `Lifecycle email contact is not configured (LIFECYCLE_EMAILS_CONTACT_*): first site reminders not sent`
  - per-user error: `First site reminder failed for user <userId>`
  - summary: `First site reminder summary: eligible=N, sent=N, failed=N, skippedDisabled=N, skippedUnsubscribed=N, skippedAlreadySent=N, skippedContactNotConfigured=N, errored=N`
- Eligibility (plan D3): registered between 24 h and 72 h before the run, precisely `created_at > now − 72 h` and `created_at <= now − 24 h`; not unsubscribed; **no site at all** (any `creation_mode`, any `status`), and **no `first-site-reminder` ledger row in any status**. The row is account-scoped (`related_entity_id IS NULL`).
- Nothing runs the job or the sweeper automatically on this stack (no cron locally): every email and ledger row below comes from the step you just ran.

Commands use `curl`, `jq`, `psql`, `openssl`, `perl` and `docker compose`. Run everything from the repository root, in **one shell session** (the scenarios reuse variables and functions; the snippets work in bash and zsh). Define once:

```bash
DB="postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db"
dc() { docker compose --env-file .env.e2e -f docker-compose.e2e.yml "$@"; }
JOB=./dist/src/notifications/adapters/primary/sendDailyLifecycleReminders.script.js
SWEEPER=./dist/src/notifications/adapters/primary/retryLifecycleEmailDeliveries.script.js
PREVIEW=./dist/src/notifications/adapters/primary/sendLifecycleEmailPreview.script.js
SUBJ='Renseignez votre premier site sur Bénéfriches !'   # compared after turning NBSP into a space

# Run the daily job inside the api container (same env as the running API).
# Usage: job [-e VAR=value ...] [--dry-run]. The -e overrides apply to that one process only.
# Prints the job's own lines and the exit code; the full output is in /tmp/job.log.
job() {
  local opts=()
  while [ "$1" = "-e" ]; do opts+=(-e "$2"); shift 2; done
  dc exec -T "${opts[@]}" api node "$JOB" "$@" > /tmp/job.log 2>&1; local rc=$?
  grep -iE 'first site reminder|contact is not configured|sendDailyLifecycleReminders' /tmp/job.log
  echo "exit code: $rc"
}
# 1 if the last job run listed this address as eligible (dry run), else 0.
listed() { grep -cF "Eligible for first site reminder: userId=${2:-$USER_ID}, email=${1:-$EMAIL}," /tmp/job.log; }

# Run the retry sweeper (ticket 04), same override convention as job.
sweep() {
  local opts=()
  while [ "$1" = "-e" ]; do opts+=(-e "$2"); shift 2; done
  dc exec -T "${opts[@]}" api node "$SWEEPER" > /tmp/sweep.log 2>&1; local rc=$?
  grep -E 'retry summary|Retry failed' /tmp/sweep.log; echo "exit code: $rc"
}
mc_down() { dc stop mailcatcher; }
mc_up() { dc start mailcatcher && until curl -sf -o /dev/null http://localhost:1081/messages; do sleep 1; done; echo "mailcatcher up"; }

# Register a fresh user named Grégoire Bailleux (as in the mockup); sets USER_ID, EMAIL, JAR.
register() {
  USER_ID=$(uuidgen | tr 'A-Z' 'a-z')
  EMAIL="qa-lifecycle05-$(date +%s)-$RANDOM@example.com"
  JAR="/tmp/qa05-$USER_ID.cookies"
  curl -s -c "$JAR" -o /tmp/register-response.json -w '%{http_code}\n' -X POST http://localhost:3001/api/auth/register \
    -H "Content-Type: application/json" \
    -d "{
      \"id\": \"$USER_ID\",
      \"email\": \"$EMAIL\",
      \"firstName\": \"Grégoire\",
      \"lastName\": \"Bailleux\",
      \"structureType\": \"company\",
      \"structureActivity\": \"other\",
      \"structureName\": \"ADEME\",
      \"personalDataStorageConsented\": true,
      \"personalDataAnalyticsUseConsented\": false,
      \"personalDataCommunicationUseConsented\": false,
      \"subscribedToNewsletter\": false
    }"
}
# Move the current user's registration into the past: backdate <hours> [minutes] [user id].
backdate() {
  psql "$DB" -At -c "UPDATE users SET created_at = now() - interval '$1 hours ${2:-0} minutes' WHERE id = '${3:-$USER_ID}' RETURNING created_at;"
}
# Insert a site owned by the current user: add_site <creation_mode> <status>. Prints the site id.
add_site() {
  local sid=$(uuidgen | tr 'A-Z' 'a-z')
  psql "$DB" -q -c "INSERT INTO sites (id, name, created_by, creation_mode, nature, surface_area, owner_structure_type, status, created_at)
    VALUES ('$sid', 'QA 05 site', '${3:-$USER_ID}', '$1', 'FRICHE', 1000, 'company', '$2', now() - interval '12 hours');"
  echo "$sid"
}

# The current user's first-site-reminder rows: status | attempts | related_entity_id | sent_at | error_message
reminder_rows() {
  psql "$DB" -At -F ' | ' -c "SELECT status, attempts, coalesce(related_entity_id::text, 'NULL'),
      coalesce(sent_at::text, 'NULL'), coalesce(error_message, 'NULL')
    FROM lifecycle_email_deliveries WHERE user_id = '${1:-$USER_ID}' AND email_type = 'first-site-reminder' ORDER BY created_at;"
}
# Reminder emails MailCatcher holds for an address, and the newest one's id.
reminder_count() {
  curl -s http://localhost:1081/messages | jq --arg e "${1:-$EMAIL}" --arg s "$SUBJ" \
    '[.[] | select((.subject | gsub(" "; " ")) == $s and (.recipients[] | contains($e)))] | length'
}
reminder_id() {
  curl -s http://localhost:1081/messages | jq -r --arg e "${1:-$EMAIL}" --arg s "$SUBJ" \
    '[.[] | select((.subject | gsub(" "; " ")) == $s and (.recipients[] | contains($e)))] | max_by(.id) | .id'
}
# Plain-text part of a message, CRs stripped, NBSP turned into plain spaces (checked separately in S9).
plain() { curl -s "http://localhost:1081/messages/$1.plain" | tr -d '\r' | perl -CSD -pe 's/\x{00A0}/ /g'; }

# The plan's D3 eligibility, written by hand: who the job should pick right now.
cohort() {
  psql "$DB" -At -c "SELECT u.email FROM users u
    WHERE u.created_at > now() - interval '72 hours' AND u.created_at <= now() - interval '24 hours'
      AND u.lifecycle_emails_unsubscribed_at IS NULL
      AND NOT EXISTS (SELECT 1 FROM sites s WHERE s.created_by = u.id)
      AND NOT EXISTS (SELECT 1 FROM lifecycle_email_deliveries d WHERE d.user_id = u.id AND d.email_type = 'first-site-reminder')
    ORDER BY u.created_at;"
}

# Unsubscribe token, as in 03 S9.
SECRET=e2e-tests-unsubscribe-secret
sign() { printf 'v1.%s.%s' "$1" "$(printf '%s' "lifecycle-emails-unsubscribe:v1:$1" | \
  openssl dgst -sha256 -hmac "$2" -binary | base64 | tr '+/' '-_' | tr -d '=')"; }
```

(`tr` lowercases the UUID, as in 03: macOS `uuidgen` prints uppercase.) Offsets are measured from the database clock (`now()` in `backdate`), the window from the `api` container's clock. They are the same machine; the few seconds the job takes to boot are why the boundary checks in S4 use a 5-minute margin rather than the exact instant (the exact `>` / `<=` semantics are pinned by integration tests, S17).

The job is a new process each time, so an `-e` override (`job -e LIFECYCLE_EMAILS_ENABLED=false`) never touches the running API. If you need a Node one-liner with environment access inside the container, write the script to a file and pipe it in (`dc exec -T api node --input-type=module < /tmp/snippet.mjs`) rather than putting it inline: a local hook blocks commands whose text contains env-access code. No scenario below needs one.

If Docker access is not available, this guide cannot be run: the job, the sweeper and the per-process overrides all need `docker compose exec`. Fall back on S17's automated tests.

## S0 — Preconditions: the script is built, the contact is configured, the cohort is drained

1. The scripts are in the image: `dc exec -T api ls "$JOB" "$SWEEPER" "$PREVIEW"`. Observe: the three paths are printed. If `$JOB` is missing, stop: the stack predates this ticket.
2. The contact reaches the container: `for v in FIRST_NAME LAST_NAME ROLE PHONE EMAIL; do printf '%s=' "$v"; dc exec -T api printenv "LIFECYCLE_EMAILS_CONTACT_$v"; done`. Observe:
   ```
   FIRST_NAME=Mathilde
   LAST_NAME=Lefèvre
   ROLE=Chargée de déploiement
   PHONE=01 23 45 67 89
   EMAIL=mathilde.lefevre@example.com
   ```
   Keep them for later checks: `CONTACT_EMAIL=$(dc exec -T api printenv LIFECYCLE_EMAILS_CONTACT_EMAIL)`.
3. Cohort against real data, dry run: `cohort | tee /tmp/cohort-s0.txt | wc -l`, then `job --dry-run`. Observe:
   - first the window line, `[DRY RUN] First site reminders: registered after <T1> and at or before <T2>`;
   - one `[DRY RUN] Eligible for first site reminder: …` line per user, and their addresses are exactly the ones in `/tmp/cohort-s0.txt` (`grep -o 'email=[^,]*' /tmp/job.log | cut -d= -f2 | sort | diff - <(sort /tmp/cohort-s0.txt) && echo SAME`, prints `SAME`);
   - the summary `[DRY RUN] First site reminder summary: eligible=<wc -l count>, sent=0, …` with every other counter `0`;
   - `exit code: 0`.
   This is the pre-launch check the ticket describes (dry run against real data), run against the e2e database.
4. The window is 72 h → 24 h before the run: copy `<T1>` and `<T2>` from the window line, then `psql "$DB" -At -c "SELECT '<T2>'::timestamptz - '<T1>'::timestamptz, now() - '<T2>'::timestamptz;"`. Observe: `2 days` and `1 day 00:0x:xx` (24 h plus the seconds since the run).
5. Drain: `job`. Observe: `sent=` equals the dry run's `eligible=`, `failed=0`, `errored=0`, `exit code: 0` (these are leftover e2e users; their reminders land in MailCatcher). Then `cohort | wc -l`. Observe: `0`.
6. Drain the sweeper too (so S12's counts are yours): `sweep`. Observe: `failed=0`, `abandoned=0`, `errored=0`, `exit code: 0`.

From here on, the cohort holds only the users you create. Other users you created in earlier scenarios may still be eligible when you run the job: always check **your** user with `listed`, `reminder_count` and `reminder_rows`, not only the totals.

## S1 — A person who registered 36 hours ago and created no site receives the reminder

Ticket scenario 1; ACs "a daily standalone script computes the eligible cohort and sends the reminder", "eligibility requires registration between 24 and 72 hours before the run".

1. `register`. Observe: `201`. `backdate 36`. Observe: a timestamp 36 h ago.
2. `cohort | grep -c "$EMAIL"`. Observe: `1`.
3. `job`. Observe:

## S3 — Two runs at the same time send one reminder each

The overlapping-run case (a manual `scalingo run` during the cron run). Plan D8: the second run is stopped by the sender's `hasDelivery` check or, at worst, by the unique index (counted `errored`, no email).

1. Create three eligible users:
   ```bash
   IDS=(); EMAILS=()
   for i in 1 2 3; do register; backdate 36 > /dev/null; IDS+=("$USER_ID"); EMAILS+=("$EMAIL"); done
   ```
   Observe: three `201`. `cohort | wc -l` → `3` (or more if older QA users are still eligible).
2. Start two jobs together:
   ```bash
   dc exec -T api node "$JOB" > /tmp/job-a.log 2>&1 &
   dc exec -T api node "$JOB" > /tmp/job-b.log 2>&1 &
   wait; grep -h 'First site reminder summary' /tmp/job-a.log /tmp/job-b.log
   ```
   Observe: two summary lines, `failed=0` in both, and the two `sent=` values **add up to 3** (plus any other eligible user). How the rest splits depends on timing: the slower run shows the users it lost as `skippedAlreadySent=` or `errored=` (unique index), or does not see them at all (smaller `eligible=`).
3. `for e in "${EMAILS[@]}"; do reminder_count "$e"; done`. Observe: `1`, `1`, `1`, never `2`.
4. `for id in "${IDS[@]}"; do reminder_rows "$id"; done`. Observe: three rows, each `sent | 1 | NULL | …`.

## S4 — The window: inside, before, after, and the boundaries

ACs "eligibility requires registration between 24 and 72 hours before the run"; plan D2 (`created_at > now − 72 h` and `<= now − 24 h`).

1. Create seven users, one per offset: 36 h (inside), 12 h (too recent, "before the window"), 80 h (too old, "after the window"), 24 h 05 min (just inside the lower bound), 23 h 55 min (just outside it), 71 h 55 min (just inside the upper bound), 72 h 05 min (just outside it):
   ```bash
   W=()
   for off in "36 0" "12 0" "80 0" "24 5" "23 55" "71 55" "72 5"; do
     register > /dev/null; backdate "${off% *}" "${off#* }" > /dev/null
     W+=("$off|$EMAIL")

   ```
2. Right away, `job --dry-run`, then:
   ```bash
   for w in "${W[@]}"; do echo "${w%%|*} (h min) → listed=$(grep -cF "email=${w#*|}," /tmp/job.log)"; done
   ```
   Observe:

   | Registered | Listed |
   | --- | --- |
   | 36 h ago | `1` |
   | 12 h ago (before the window) | `0` |
   | 80 h ago (after the window) | `0` |
   | 24 h 05 min ago | `1` |
   | 23 h 55 min ago | `0` |
   | 71 h 55 min ago | `1` |
   | 72 h 05 min ago | `0` |

   The `[DRY RUN] … summary` says `eligible=` at least `3`, and `cohort` lists the same three addresses.

   Run step 2 within a few minutes of step 1: the 23 h 55 min user enters the window 5 minutes later, and the 71 h 55 min one leaves it. (The 23 h 55 min user then becomes eligible and shows up in later scenarios' totals; always check your own user.)

## S8 — An existing reminder row in any status excludes; so does unsubscribing

ACs "a user who already has a ledger row for this email type, in any status (including `failed` and `abandoned`), is excluded" and "an unsubscribed user is excluded".

1. Four eligible users, each with a hand-written `first-site-reminder` row in one status:
   ```bash
   ROW_IDS=(); ROW_EMAILS=()
   for st in pending sent failed abandoned; do
     register > /dev/null; backdate 36 > /dev/null
     psql "$DB" -q -c "INSERT INTO lifecycle_email_deliveries (id, user_id, email_type, related_entity_id, status, created_at, sent_at, error_message, attempts, last_attempted_at)
       VALUES ('$(uuidgen | tr 'A-Z' 'a-z')', '$USER_ID', 'first-site-reminder', NULL, '$st', now() - interval '1 hour',
               $( [ "$st" = sent ] && echo "now() - interval '1 hour'" || echo NULL ), $( [ "$st" = failed ] || [ "$st" = abandoned ] && echo "'SMTP down'" || echo NULL ),
               $( [ "$st" = abandoned ] && echo 5 || echo 1 ), now() - interval '1 minute');"
     ROW_IDS+=("$USER_ID"); ROW_EMAILS+=("$EMAIL"); echo "$st → $EMAIL"
   done
   ```
   (`last_attempted_at` one minute ago keeps the `pending` row out of the sweeper's reach, which needs 15 minutes.)
2. An eligible user who unsubscribed (signed link, as in 03 S9):
   ```bash
   register > /dev/null; backdate 36 > /dev/null
   curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:3001/api/lifecycle-emails/unsubscribe \
     -H "Content-Type: application/json" -d "{\"token\": \"$(sign "$USER_ID" "$SECRET")\"}"
   UNSUB_ID=$USER_ID; UNSUB_EMAIL=$EMAIL
   ```
