## Setup and assumptions

The app is already running at `http://localhost:3001` (the e2e stack, `docker-compose.e2e.yml` + `.env.e2e`, from the repository root). It must have been **built from this branch after ticket 03 was implemented** (`make e2e-up-build`), so that the `api` and `web` images contain the unsubscribe endpoint and page, and the `api` container has the new `LIFECYCLE_EMAILS_UNSUBSCRIBE_SECRET` variable. Nothing below starts, stops or restarts it.

Fixed facts about this running stack, taken from `.env.e2e` / `docker-compose.e2e.yml`:

- Web app / API (proxied): `http://localhost:3001` — `POST /api/auth/register` is the registration endpoint (see `apps/e2e-tests/fixtures/auth.fixtures.ts` → `createTestUserViaApi`); `POST /api/lifecycle-emails/unsubscribe` is the new unsubscribe endpoint (body `{ "token": "…" }`, `204` on success, `400 { error: "INVALID_UNSUBSCRIBE_TOKEN", message }` on a bad token).
- Unsubscribe link in every lifecycle email: `${WEBAPP_URL}/emails/desinscription?token=<token>`, with `WEBAPP_URL=http://localhost:3001`. That is a public web-app page; on load it `POST`s the token to the endpoint above.
- Token format (plan D1): `v1.<userId>.<base64url(HMAC-SHA256(secret, "lifecycle-emails-unsubscribe:v1:" + userId))>`, no timestamp, not stored in the database.
- `LIFECYCLE_EMAILS_UNSUBSCRIBE_SECRET=e2e-tests-unsubscribe-secret` in `.env.e2e`, forwarded to the `api` service.
- MailCatcher UI/API: `http://localhost:1081`.
- Postgres: `postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db`.
- Inside the running `api` container, `LIFECYCLE_EMAILS_ENABLED=true` — the kill switch is **on**, so a genuine registration sends a welcome email.
- The endpoint is throttled to **10 requests per minute** (same as the auth-token routes). If a `curl` below returns `429`, wait a minute and re-run the step; it is not a failure of the scenario.

Commands use `curl`, `jq`, `psql`, `openssl` and `docker compose`. Run everything from the repository root, in one shell session (the scenarios reuse variables). Define once:

```bash
DB="postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db"
dc() { docker compose --env-file .env.e2e -f docker-compose.e2e.yml "$@"; }
```

Check the running `api` container has the secret (confirms the stack was rebuilt with ticket 03): `dc exec -T api printenv LIFECYCLE_EMAILS_UNSUBSCRIBE_SECRET`. Observe: `e2e-tests-unsubscribe-secret`. If it prints nothing, stop — the stack predates this ticket.

API scripts (the ticket 02 preview script, and the one-off sender call in S12) are run **inside the `api` container** with `dc exec -T api node …`: its working directory is `/app/apps/api`, `dist/` is already built, and its environment (container-internal `DATABASE_URL`, `SMTP_HOST=mailcatcher`, kill switch on, unsubscribe secret) is exactly the one the running API uses. If Docker access is not available, run them on the host instead with the env from `docs/qa/lifecycle-emails/02.md` Setup, keeping `LIFECYCLE_EMAILS_UNSUBSCRIBE_SECRET` from `.env.e2e` (a different secret would sign links the running API rejects) and, for S12 only, `export LIFECYCLE_EMAILS_ENABLED=true`.

Registration payload shape (mirrors `createTestUserData` in `apps/e2e-tests/fixtures/auth.fixtures.ts`):

```bash
  -H "Content-Type: application/json" \
  -d "{
    \"id\": \"$USER_ID\",
    \"email\": \"$EMAIL\",
    \"firstName\": \"Jean\",
    \"lastName\": \"Dupont\",
```

(`tr` lowercases the UUID: macOS `uuidgen` prints uppercase, and the token and the `users.id` column use the lowercase form.) `curl` is never given the `-c`/`-b` flags, so none of the requests below carries the access-token cookie the registration response sets — every call is **unauthenticated**.

Finding the welcome email in MailCatcher by recipient + exact subject (mirrors `waitForEmail` in `apps/e2e-tests/fixtures/helpers/mail-catcher.ts`; MailCatcher is never purged between runs, so always filter by exact subject, not recipient alone):

```bash
MSG_ID=$(curl -s http://localhost:1081/messages | \
  jq -r --arg email "$EMAIL" --arg subj "Bienvenue chez Bénéfriches" \
  '[.[] | select(.subject == $subj and (.recipients[] | contains($email)))] | max_by(.id) | .id')
```

Extracting the unsubscribe link and its token from that message's plain-text part:

```bash
UNSUB_URL=$(curl -s http://localhost:1081/messages/$MSG_ID.plain | tr -d '\r' | \
  grep -o 'http[^ ]*/emails/desinscription?token=[^ ]*' | tail -1)
TOKEN=${UNSUB_URL##*token=}
echo "$UNSUB_URL"; echo "$TOKEN"
```

Reading a user's unsubscribe column:

```bash
psql "$DB" -At -c "SELECT coalesce(lifecycle_emails_unsubscribed_at::text, 'NULL') FROM users WHERE id = '$USER_ID';"
```

Browser checks use a **private/incognito window** (no Bénéfriches session cookie) with DevTools open on the **Network** tab.

## S6 — A tampered signature fails and changes nothing

1. Register a fresh user, resolve `$MSG_ID`, extract `$UNSUB_URL` / `$TOKEN`. Baseline the column. Observe: `NULL`.
2. Build a token with **one character of the signature changed** (the first signature character — every bit of it is significant, unlike the last base64url character, see the note below):
   ```bash
   PREFIX=${TOKEN%.*}; SIG=${TOKEN##*.}
   FIRST_CHAR=$(printf '%s' "$SIG" | cut -c1); [ "$FIRST_CHAR" = "A" ] && R=B || R=A
   TAMPERED="$PREFIX.$R$(printf '%s' "$SIG" | cut -c2-)"
   echo "$TOKEN"; echo "$TAMPERED"
   ```
   Observe: the two strings differ by exactly one character.
3. In a private window, open `http://localhost:3001/emails/desinscription?token=$TAMPERED` (substitute the value). Observe:
   - tab title `Lien de désinscription invalide - Bénéfriches`;
   - H1 **Ce lien de désinscription ne fonctionne pas**;
   - "Il est peut-être incomplet. Cliquez à nouveau sur « vous désinscrire » en bas de l’un de nos e-mails, ou copiez le lien en entier dans votre navigateur.";
   - "Vos préférences n’ont pas été modifiées.";
   - a contact line for the Bénéfriches team;
   - no "Réessayer" button (that belongs to the technical-error state, S15);
   - Network: `POST /api/lifecycle-emails/unsubscribe` → `400`.
4. Through the API:
   ```bash
   curl -s -w '\n%{http_code}\n' -X POST http://localhost:3001/api/lifecycle-emails/unsubscribe \
     -H "Content-Type: application/json" -d "{\"token\": \"$TAMPERED\"}"
   ```
   Observe: body `{"error":"INVALID_UNSUBSCRIBE_TOKEN","message":"Invalid unsubscribe token"}`, status `400`.
5. Re-run the Setup `psql` command. Observe: still `NULL` — the user's preferences are unchanged.
6. Control: the untampered `$TOKEN` still works for this user — POST it as in S4 step 3. Observe: `204`, and the column now holds a timestamp.

Note for the implementer: the plan's unit/integration tests tamper the **last** character. For a 32-byte HMAC, the last of the 43 base64url characters carries 2 unused padding bits, so e.g. `A`→`B` can decode to the same bytes. If verification decodes the signature before comparing bytes, that test could pass or fail depending on the character; comparing the recomputed base64url **string** (or tampering a middle character in the test) avoids the ambiguity. Step 2 above sidesteps it.

## S9 — The token is signed and verified server-side with the dedicated secret

1. Register a fresh user, resolve `$MSG_ID`, extract `$TOKEN`. Baseline the column. Observe: `NULL`.
2. Recompute the expected token from nothing but the user id and the e2e secret:
   ```bash
   SECRET=e2e-tests-unsubscribe-secret
   sign() { printf 'v1.%s.%s' "$1" "$(printf '%s' "lifecycle-emails-unsubscribe:v1:$1" | \
     openssl dgst -sha256 -hmac "$2" -binary | base64 | tr '+/' '-_' | tr -d '=')"; }
   ```

## S10 — The token does not expire

The token carries no date, so no amount of waiting can expire it. Checked three ways:

1. Structure: reuse `$TOKEN` from S9. `echo "$TOKEN" | awk -F. '{print NF}'`. Observe: `3` parts — `v1`, the user id, the signature; S9 step 2 showed the signature is computed from the user id and the secret only, with no timestamp input.
2. Code: `grep -nE 'DateProvider|Date\.now\(|new Date\(|expiresIn' apps/api/src/notifications/adapters/secondary/unsubscribe-token/HmacUnsubscribeTokenService.ts`. Observe: no output — the token service has no clock to check an expiry against.
3. An "old" link still works: pick the oldest non-unsubscribed user in this database (created on an earlier e2e run, before any of today's tokens existed) and sign a token for it as if it had been in an email sent back then:
   ```bash
   OLD_ID=$(psql "$DB" -At -c "SELECT id FROM users WHERE lifecycle_emails_unsubscribed_at IS NULL ORDER BY created_at ASC LIMIT 1;")
   psql "$DB" -At -c "SELECT created_at FROM users WHERE id = '$OLD_ID';"
   curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:3001/api/lifecycle-emails/unsubscribe \
     -H "Content-Type: application/json" -d "{\"token\": \"$(sign "$OLD_ID" "$SECRET")\"}"
   ```
   Observe: `204`, and `SELECT lifecycle_emails_unsubscribed_at FROM users WHERE id = '$OLD_ID'` now holds today's timestamp. (Skip this step if the first query returns no row.)

The token is also identical for every email to the same user (S9 step 2 is deterministic): a forwarded or older email keeps working. Covered at unit level by "signs the same user to the same token every time" in `HmacUnsubscribeTokenService.spec.ts`, whose header notes why there is deliberately no expiry test.

## S12 — After unsubscribing, the sender sends no lifecycle email

The welcome email fires only once per user (on registration), and there is no HTTP route that replays the account-created event. So this scenario calls the real `SendWelcomeEmailUseCase` → `LifecycleEmailSender` path directly, inside the `api` container, where the kill switch is on. The ledger row from the registration is deleted first so the dedup check cannot be what stops the send.

Define the one-off call (it boots `AppModule` like the preview script does):

```bash
send_welcome() {
  dc exec -T -e QA_USER_ID="$1" -e QA_EMAIL="$2" api node --input-type=module -e '
    import { NestFactory } from "@nestjs/core";
    const { AppModule } = await import("./dist/src/app.module.js");
    const { SendWelcomeEmailUseCase } = await import("./dist/src/notifications/core/usecases/sendWelcomeEmail.usecase.js");
    const app = await NestFactory.createApplicationContext(AppModule, { logger: ["error", "warn"] });
    const result = await app.get(SendWelcomeEmailUseCase).execute({ userId: process.env.QA_USER_ID, userEmail: process.env.QA_EMAIL });
    console.log("outcome:", result.isSuccess() ? result.getData().outcome : result.getError());
    await app.close();
  '
}
welcome_count() {
  curl -s http://localhost:1081/messages | jq --arg email "$1" \
    '[.[] | select(.subject == "Bienvenue chez Bénéfriches" and (.recipients[] | contains($email)))] | length'
}
```

Unsubscribed user:

1. Register a fresh user, resolve `$MSG_ID`, extract `$TOKEN`, then unsubscribe with the S4 step 3 `curl`. Observe: `204`; the column holds a timestamp.
2. Baseline: `welcome_count "$EMAIL"`. Observe: `1`.
3. Remove the registration's ledger row: `psql "$DB" -c "DELETE FROM lifecycle_email_deliveries WHERE user_id = '$USER_ID';"`. Observe: `DELETE 1`.
4. `send_welcome "$USER_ID" "$EMAIL"`. Observe: `outcome: skipped-unsubscribed`.
5. After a few seconds, `welcome_count "$EMAIL"`. Observe: still `1` — no email arrived.
6. `psql "$DB" -At -c "SELECT count(*) FROM lifecycle_email_deliveries WHERE user_id = '$USER_ID';"`. Observe: `0` — nothing was written either.

Control — same path, subscribed user (proves the call above really reaches the mailer when the flag is not set):

7. Register another fresh user (re-run the registration command; new `$USER_ID` / `$EMAIL`). `psql "$DB" -c "DELETE FROM lifecycle_email_deliveries WHERE user_id = '$USER_ID';"`. Observe: `DELETE 1`.
8. `send_welcome "$USER_ID" "$EMAIL"`. Observe: `outcome: sent`, and after a few seconds `welcome_count "$EMAIL"` is `2`.

The check lives in `LifecycleEmailSender`, before any per-type logic, so it applies to every lifecycle email type including the D+3/D+7 reminders added later (none exist yet to trigger here). Covered at unit level by "does not send to an unsubscribed user" in `apps/api/src/notifications/core/services/lifecycleEmailSender.spec.ts`, and end-to-end by "stops every later lifecycle email once unsubscribed" in `apps/api/src/notifications/adapters/primary/notifications.controller.integration-spec.ts`.
