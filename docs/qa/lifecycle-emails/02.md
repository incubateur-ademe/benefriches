## Setup and assumptions

The app is already running at `http://localhost:3001` (the e2e stack, `docker-compose.e2e.yml` + `.env.e2e`, from the repository root). Nothing below starts, stops or restarts it.

Fixed facts about this running stack, taken from `.env.e2e` / `docker-compose.e2e.yml`:

- Web app / API (proxied): `http://localhost:3001` — `POST /api/auth/register` is the registration endpoint (see `apps/e2e-tests/fixtures/auth.fixtures.ts` → `createTestUserViaApi`).
- MailCatcher UI/API: `http://localhost:1081`.
- Postgres: `postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db`.
- Inside the running `api` container, `LIFECYCLE_EMAILS_ENABLED=true` — the kill switch is **on** for that container and governs any _genuine_, event-driven send (e.g. a real registration). This cannot be flipped without restarting the container, which this guide must not do.

The preview script (`apps/api/src/notifications/adapters/primary/sendLifecycleEmailPreview.script.ts`, compiled to `apps/api/dist/src/notifications/adapters/primary/sendLifecycleEmailPreview.script.js`) is a standalone one-off script, not an HTTP route — it is not reachable by hitting the running containers. This guide's execution environment has no Docker socket access (no `docker compose exec`), so the script is run directly on the host, from the already-built `apps/api/dist` in this checkout, against the e2e stack's host-mapped Postgres and SMTP ports. The compiled script boots the full `AppModule` (`NestFactory.createApplicationContext`), so it needs the same environment variables the `api` container has — sourced from the repository's own `.env.e2e` — with three host-networking adjustments: `DATABASE_URL` unset so the DB client falls back to `DATABASE_PORT`/`DATABASE_USER`/`DATABASE_PASSWORD`/`DATABASE_DB_NAME` against `localhost` (the container-internal `DATABASE_URL` points at hostname `postgres`, unreachable from the host), `SMTP_HOST` pointed at `localhost` instead of the container-internal `mailcatcher` hostname, and `LIFECYCLE_EMAILS_ENABLED` unset to demonstrate the kill switch being off for the script's own process (independent of the container, which stays on and is what makes S8's genuine send work).

Run once, from the repository root, before any scenario below:

```bash
set -a
source .env.e2e
unset DATABASE_URL
export SMTP_HOST=localhost
unset LIFECYCLE_EMAILS_ENABLED
set +a
cd apps/api
```

Every scenario below invokes the script from `apps/api` as:

```bash
node ./dist/src/notifications/adapters/primary/sendLifecycleEmailPreview.script.js --type=<type> --to=<address> [--to=<address> …]
```

Registration payload shape, for scenarios that need a real user (mirrors `createTestUserData` in `apps/e2e-tests/fixtures/auth.fixtures.ts`; run from the repository root, not `apps/api`):

```bash
USER_ID=$(uuidgen)
EMAIL="qa-lifecycle02-$(date +%s)-$RANDOM@example.com"
curl -s -o /tmp/register-response.json -w '%{http_code}\n' -X POST http://localhost:3001/api/auth/register \
  -H "Content-Type: application/json" \
  -d "{
    \"id\": \"$USER_ID\",
    \"email\": \"$EMAIL\",
    \"firstName\": \"Jean\",
    \"lastName\": \"Dupont\",
    \"structureType\": \"company\",
    \"structureActivity\": \"other\",
    \"structureName\": \"ADEME\",
    \"personalDataStorageConsented\": true,
    \"personalDataAnalyticsUseConsented\": false,
    \"personalDataCommunicationUseConsented\": false,
    \"subscribedToNewsletter\": false
  }"
```

Finding a message in MailCatcher by recipient + exact subject (mirrors `waitForEmail` in `apps/e2e-tests/fixtures/helpers/mail-catcher.ts`; MailCatcher is never purged between runs, so always filter by exact subject, not recipient alone):

```bash
MSG_ID=$(curl -s http://localhost:1081/messages | \
  jq -r --arg email "$EMAIL" --arg subj "Bienvenue chez Bénéfriches" \
  '[.[] | select(.subject == $subj and (.recipients[] | contains($email)))] | max_by(.id) | .id')
```

## S1 — Preview sends with the kill switch off

1. From `apps/api`, with the Setup env applied (`LIFECYCLE_EMAILS_ENABLED` unset — the `.env.example` default), run:
   ```bash
   EMAIL="qa-preview-s1-$(date +%s)-$RANDOM@example.com"
   node ./dist/src/notifications/adapters/primary/sendLifecycleEmailPreview.script.js --type=welcome --to="$EMAIL"
   echo "exit code: $?"
   ```
   Observe: `exit code: 0`.
2. Poll MailCatcher for a message to `$EMAIL`: `curl -s http://localhost:1081/messages | jq --arg email "$EMAIL" '[.[] | select(.recipients[] | contains($email))]'`. Observe: within a few seconds, the array contains at least one entry.
3. Resolve `$MSG_ID` with the lookup command from Setup (`$subj` = `Bienvenue chez Bénéfriches`). Observe: `MSG_ID` is a non-empty number, not `null` — a message addressed to `$EMAIL` with subject exactly `Bienvenue chez Bénéfriches` was delivered, even though the kill switch was off for the process that sent it.

## S2 — Two recipients both receive and both are logged

## S8 — A preview does not block a later genuine send

The ticket's Given ("a real registered user exists … with no welcome row") and When ("the preview script is run … and afterwards the genuine welcome path fires") are reproduced here as: pick an address with no user yet, preview it first, then register that same address as a real user — registration is what fires the genuine welcome path (there is no HTTP route to replay a domain event on an already-registered user, and a real registration synchronously sends its welcome email inline). This achieves the same ordering the ticket describes (preview before the genuine send) while staying reachable from the running app.

1. Pick a fresh address not yet used by any user: `EMAIL="qa-preview-s8-$(date +%s)-$RANDOM@example.com"`.
2. From `apps/api`, run the preview script for that address: `node ./dist/src/notifications/adapters/primary/sendLifecycleEmailPreview.script.js --type=welcome --to="$EMAIL"`. Observe: exit code `0`.
3. Confirm no ledger row exists yet for this address (no user row exists to own one): `psql "postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db" -c "SELECT count(*) FROM lifecycle_email_deliveries d JOIN users u ON u.id = d.user_id WHERE u.email = '$EMAIL';"`. Observe: `0`.
4. Register that exact address as a real user, from the repository root, using the Setup registration command but with `EMAIL` fixed to the value from step 1 (adjust the `-d` payload's `"email"` field accordingly) and a fresh `USER_ID=$(uuidgen)`. Observe: the response status printed by `-w` is `201`.
5. Confirm the genuine email arrived: resolve `$MSG_ID` with the Setup lookup command (recipient `$EMAIL`, subject `Bienvenue chez Bénéfriches`). Observe: a non-empty `$MSG_ID`.
6. Query the ledger for the real send: `psql "postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db" -c "SELECT email_type, status, sent_at FROM lifecycle_email_deliveries WHERE user_id = '$USER_ID';"`. Observe: **exactly one** row, with `email_type = welcome` and `status = sent` — the earlier preview run neither wrote a row of its own nor made this genuine send look like a duplicate (no conflict, no second row).
