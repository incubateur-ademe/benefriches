## Setup and assumptions

Ticket 07 is a **pure refactor**: the Synthèse headline derivation (`getKeyImpactIndicatorsList`), its helper `getPercentageDifference` (its other helper, `filterByName`, was already in `packages/shared/src/filter-by-name` on `main`; 07 only adds a spec for it), the evaluation-period crop (`cropImpactsByEvaluationPeriod`, `cropUrbanSprawlSimulationByEvaluationPeriod`) and the 30/50 default (`getDefaultEvaluationPeriodInYears`) move from `apps/web` to `packages/shared`, with two small extractions (`getSummaryHeadlineIndicators`, `getBreakEvenHorizon`). Nothing a user sees may change. This guide proves it in two ways:

- **parity on the running app**: the same projects captured on the commit **before** the change (S1–S2) and after it (S3–S4), compared byte for byte;
- **code and test checks**: the code lives where the plan says, web has no copy left, `shared` stays framework-free, the characterization specs pin the old behaviour and pass unmodified (S5–S8).

Source of truth: `.agents/tasks/lifecycle-emails/issues/07-move-key-impact-indicators-to-shared.md` and its `.plan.md` (decisions D1–D7, "Resolved open questions": the crop and the default move in 07, and so do the D3 extractions).

**Order matters.** S1 and S2 must run on the **baseline** commit, before the implementation reaches the running stack. This guide was written at `54159d337` (ticket 06's docs commit), the baseline. If ticket 07 is already implemented in this worktree when you start, S0 step 3 builds the stack from a separate worktree of the baseline instead.

The app runs at `http://localhost:3001` (the e2e stack, `docker-compose.e2e.yml` + `.env.e2e`, compose project `benefriches-e2e`). Unlike 06, this guide **rebuilds** the `api` and `web` containers twice (baseline, then change) with `make e2e-up-build` or its equivalent: the web bundle is the thing under test. The Postgres volume (`benefriches_pg_e2e_data`) survives a rebuild, so the projects created in S1 are still there in S4. Never run `make e2e-down -v` or remove that volume between S2 and S4.

Fixed facts about this stack and the code, taken from `.env.e2e`, `docker-compose.e2e.yml` and the plan:

- Web app / API (proxied): `http://localhost:3001`. `POST /api/auth/register` registers a user; the response sets the `access_token` cookie (HttpOnly, valid **7 days**: run S4 within a week of S2, or the captures fail on a login redirect). `POST /api/sites/create-express` creates an express site; a `FRICHE` gets the owner `municipality` / `Mairie de <city>`, so its avoided friche costs go to a local authority (card 3: "Gains pour la collectivité"). `POST /api/reconversion-projects` creates a custom project (body `ReconversionProjectSavePropsDto`, as in `apps/e2e-tests/fixtures/helpers/reconversion-project-creation.helpers.ts`); `POST /api/reconversion-projects/create-from-template` creates an express project (`template`: an urban template, or `PHOTOVOLTAIC_POWER_PLANT`). `GET /api/reconversion-projects/:id/impacts` returns `GetReconversionProjectImpactsResultDto` (always computed over 50 years, API-side; this ticket does not touch the API).
- Photovoltaic performance is mocked on this stack (`MOCK_PHOTOVOLTAIC_PERFORMANCE_API=true`), so photovoltaic projects are deterministic.
- Project pages (`/mes-projets/<id>/…`), all rendered from the impacts DTO by web code this ticket moves: `apercu` (the Synthèse tab: map, **ZAN card**, **break-even card**, **main indicator card**), `impacts` (Synthèse / Liste views; `?details=synthese_<code>` opens a headline's detail modal), `analyse-cout-benefice`, `analyse-couts-evites` (urban sprawl comparison, cropped by `cropUrbanSprawlSimulationByEvaluationPeriod`). Each tab has a `Durée : <n> ans` button that changes the evaluation period (range 1–50, then `Changer la durée`).
- The period a page opens on (plan D7): **30 years for a photovoltaic project, 50 otherwise**. The headline cards are derived from impacts **cropped** to that period (plan "Input: cropped impacts"). The break-even card (`ProjectBreakEvenLevelSummary.tsx`) shows:
  - `En <breakEvenYear>` / `Bilan de l’opération positif` when break-even is the first projection year;
  - `En <n> an(s)` / `Coût de l’opération compensé` / `… compenseront le coût de l’opération en <year>.` when it falls inside the period;
  - `Sur <period> ans` / `Coût de l’opération non compensé` and either `… compenseront … en <year>.` (break-even after the cropped period) or `… ne compenseront pas le coût de l’opération.` (no break-even at all).
- The main indicator (card 3) is the highest-priority indicator other than `zanCompliance` and `projectImpactBalance`, in `PRIORITY_ORDER` (renamed `KEY_IMPACT_INDICATORS_PRIORITY_ORDER`, D1). Its title and wording stay in `ProjectSummaryComparisonCard.tsx`.
- A headline modal for an indicator the project does not have makes the Impacts page fail to render (`SummaryModalWizard`'s `find(…)!`): pre-existing behaviour, not this ticket's. The capture records it as `(no modal)` and it must stay so.
