## Setup and assumptions

The app is already running at `http://localhost:3001` (the e2e stack, `docker-compose.e2e.yml` + `.env.e2e`). Nothing below starts, stops or restarts it.

Fixed facts about this running stack, taken from `.env.e2e` / `docker-compose.e2e.yml`, needed by the steps below:

- Web app / API (proxied): `http://localhost:3001` — `POST /api/auth/register` is the registration endpoint (see `apps/e2e-tests/fixtures/auth.fixtures.ts` → `createTestUserViaApi`).
- MailCatcher UI/API: `http://localhost:1081` (`MAILCATCHER_UI_PORT=1081`).
- Postgres: `postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db` (`DATABASE_PORT=5433`).
- `LIFECYCLE_EMAILS_ENABLED=true` in this stack's `.env.e2e` — the kill switch is **on** for every test below unless a scenario says otherwise. It is read once at API boot (`notifications.module.ts`), so it cannot be flipped without restarting the API container — see the notes under S3/S14.

Commands use `curl`, `jq` and `psql`. If one isn't available, the MailCatcher web UI at `http://localhost:1081` and any Postgres client are equivalents for the read-only checks.

Registration payload shape (mirrors `createTestUserData` in `apps/e2e-tests/fixtures/auth.fixtures.ts`):

```bash
USER_ID=$(uuidgen)
EMAIL="qa-lifecycle01-$(date +%s)-$RANDOM@example.com"
curl -s -o /tmp/register-response.json -w '%{http_code}\n' -X POST http://localhost:3001/api/auth/register \
  -H "Content-Type: application/json" \
  -d "{
    \"id\": \"$USER_ID\",
    \"email\": \"$EMAIL\",
    \"firstName\": \"Jean\",
    \"lastName\": \"Dupont\",
    \"structureType\": \"company\",
    \"structureActivity\": \"other\",
    \"structureName\": \"ADEME\",
    \"personalDataStorageConsented\": true,
    \"personalDataAnalyticsUseConsented\": false,
    \"personalDataCommunicationUseConsented\": false,
    \"subscribedToNewsletter\": false
  }"
```

Finding a message in MailCatcher by recipient + exact subject (mirrors `waitForEmail` in `apps/e2e-tests/fixtures/helpers/mail-catcher.ts`, which exists precisely because MailCatcher is never purged between runs and a recipient alone can match more than one email):

```bash
MSG_ID=$(curl -s http://localhost:1081/messages | \
  jq -r --arg email "$EMAIL" --arg subj "Bienvenue chez Bénéfriches" \
  '[.[] | select(.subject == $subj and (.recipients[] | contains($email)))] | max_by(.id) | .id')
```

## S1 — Welcome email arrives after registration

1. Run the registration setup command above (kill switch is already on in this stack). Observe the response status printed by `-w`: expect `201`.
2. Poll MailCatcher's message list for a message to `$EMAIL`: `curl -s http://localhost:1081/messages | jq --arg email "$EMAIL" '[.[] | select(.recipients[] | contains($email))]'`. Observe: within a few seconds, the array contains at least one entry.
3. Run the `MSG_ID` lookup command from Setup, with `$subj` fixed to `Bienvenue chez Bénéfriches`. Observe: `MSG_ID` is a non-empty number, not `null` — a message addressed to `$EMAIL` with subject exactly `Bienvenue chez Bénéfriches` exists.

## S2 — Email states the login identifier

1. Reuse (or re-run) the registration setup, capturing `$USER_ID` / `$EMAIL`, and resolve `$MSG_ID` as in S1.
2. Fetch the plain-text part: `curl -s http://localhost:1081/messages/$MSG_ID.plain`. Observe: the output contains the exact line `Votre identifiant de connexion est $EMAIL` — the address just registered with, not a placeholder or a different user's address.

## S3 — Kill switch off suppresses all sending

Not checkable against this running stack: `LIFECYCLE_EMAILS_ENABLED` is read once when the API container boots (`notifications.module.ts`), fixed to `true` for the whole lifetime of this stack, and this guide must not restart or reconfigure the stack — there is no way to flip it live or run a second API instance with it off. Covered instead by the unit test "does not send and writes no row when the kill switch is off" in `apps/api/src/notifications/core/services/lifecycleEmailSender.spec.ts`.

## S4 — Mail outage never fails a signup

Not checkable against this running stack: reproducing it requires making the SMTP/MailCatcher container unreachable, which needs Docker access this guide's execution environment does not have (it is sandboxed away from the Docker socket). Covered instead by the integration test "does not let a mailer failure propagate out of registration" in `apps/api/src/notifications/adapters/primary/sendWelcomeEmailOnUserAccountCreated.handler.integration-spec.ts`, which simulates the mailer throwing and asserts `POST /api/auth/register` still returns `201` and the ledger row is `failed`.

## S5 — Replayed account-created event sends nothing

Not checkable against this running stack: there is no HTTP route that replays a domain event, and a second `POST /api/auth/register` with the same email is rejected before any event is published (duplicate-email conflict), so the replay path is unreachable from outside the process. Covered instead by the integration test "does not send a second email when the account-created event is replayed for the same user" in `apps/api/src/notifications/adapters/primary/sendWelcomeEmailOnUserAccountCreated.handler.integration-spec.ts`.

## S6 — Unsubscribed user receives nothing

Not checkable against this running stack: setting `lifecycle_emails_unsubscribed_at` requires the unsubscribe link/endpoint, which the ticket explicitly defers to a later ticket — there is no way to unsubscribe a user _before_ their (one-time) account-created event fires during registration. Covered instead by the integration test "does not send when the user has unsubscribed from lifecycle emails" in `apps/api/src/notifications/adapters/primary/sendWelcomeEmailOnUserAccountCreated.handler.integration-spec.ts`.

## S10 — Account-scoped emails deduplicate despite NULL related entity

1. Run the registration setup command, capturing `$USER_ID`. This already leaves one row in the ledger with (`user_id = $USER_ID`, `email_type = welcome`, `related_entity_id = NULL`) — confirm it: `psql "postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db" -c "SELECT count(*) FROM lifecycle_email_deliveries WHERE user_id = '$USER_ID' AND email_type = 'welcome';"`. Observe: count is `1`.
2. Attempt to insert a second row with the same (user, type, NULL entity):
   ```bash
   psql "postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db" -c \
     "INSERT INTO lifecycle_email_deliveries (id, user_id, email_type, related_entity_id, status, created_at) VALUES ('20000000-0000-4000-8000-000000000010', '$USER_ID', 'welcome', NULL, 'pending', now());"
   ```
   Observe: PostgreSQL rejects it — `ERROR: duplicate key value violates unique constraint "lifecycle_email_deliveries_user_type_unique"`.
3. Re-run the count query from step 1. Observe: still exactly `1`.

## S11 — Entity-scoped uniqueness does not over-block different entities

1. Run the registration setup command, capturing `$USER_ID` (any user row satisfies the `user_id` foreign key; `related_entity_id` has no foreign key, so arbitrary UUIDs stand in for "site A"/"site B").
2. Insert a row for site A under a scratch email type (kept distinct from `welcome` so it doesn't interfere with S8/S10's rows for the same user):
   ```bash
   psql "postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db" -c \
     "INSERT INTO lifecycle_email_deliveries (id, user_id, email_type, related_entity_id, status, created_at) VALUES ('30000000-0000-4000-8000-000000000001', '$USER_ID', 'qa-entity-scoped-test', '40000000-0000-4000-8000-0000000000a1', 'pending', now());"
   ```
   Observe: `INSERT 0 1` — succeeds.
3. Insert a row for site B, same user and type:
   ```bash
   psql "postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db" -c \
     "INSERT INTO lifecycle_email_deliveries (id, user_id, email_type, related_entity_id, status, created_at) VALUES ('30000000-0000-4000-8000-000000000002', '$USER_ID', 'qa-entity-scoped-test', '40000000-0000-4000-8000-0000000000b2', 'pending', now());"
   ```
   Observe: `INSERT 0 1` — succeeds (this is the "does not over-block" assertion: a different `related_entity_id` is not blocked by step 2's row).
4. Attempt a second row for site A:
   ```bash
   psql "postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db" -c \
     "INSERT INTO lifecycle_email_deliveries (id, user_id, email_type, related_entity_id, status, created_at) VALUES ('30000000-0000-4000-8000-000000000003', '$USER_ID', 'qa-entity-scoped-test', '40000000-0000-4000-8000-0000000000a1', 'pending', now());"
   ```
   Observe: PostgreSQL rejects it — `ERROR: duplicate key value violates unique constraint "lifecycle_email_deliveries_user_type_entity_unique"`.
5. Confirm the final count: `psql "postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db" -c "SELECT count(*) FROM lifecycle_email_deliveries WHERE user_id = '$USER_ID' AND email_type = 'qa-entity-scoped-test';"`. Observe: `2`.

## S12 — Email is Outlook-safe and text-only

1. Run the registration setup command and resolve `$MSG_ID` as in S1.
2. Fetch the raw source: `curl -s http://localhost:1081/messages/$MSG_ID.source > /tmp/welcome-source.txt`.
3. Check both parts exist: `grep -c 'Content-Type: text/plain' /tmp/welcome-source.txt` and `grep -c 'Content-Type: text/html' /tmp/welcome-source.txt`. Observe: both return `1` or more, and `curl -s http://localhost:1081/messages/$MSG_ID.plain` returns non-empty output.
4. Check the HTML is table-based with inline styles: `grep -c '<table' /tmp/welcome-source.txt` and `grep -c 'style="' /tmp/welcome-source.txt`. Observe: both return `1` or more.
5. Check no images: `grep -c '<img' /tmp/welcome-source.txt`. Observe: `0` (`3` since BEN-32: the feature block icons, checked in `08.md`).
6. Check no flexbox/grid: `grep -Eic 'display:\s*flex|display:\s*grid|flex-' /tmp/welcome-source.txt`. Observe: `0`.
