## Setup and assumptions

The app is already running at `http://localhost:3001` (the e2e stack, `docker-compose.e2e.yml` + `.env.e2e`, from the repository root). It must have been **built from this branch after ticket 04 was implemented** (`make e2e-up-build`): the `api` image then contains the compiled sweeper script, and its entrypoint (`docker-entrypoint.sh` → `pnpm knex:migrate-latest:js`) has applied the migration adding `attempts` and `last_attempted_at` to `lifecycle_email_deliveries`.

Unlike 01–03, this guide **stops and starts the `mailcatcher` container** to simulate a mail outage (`dc stop mailcatcher` / `dc start mailcatcher`). It never restarts, rebuilds or stops the `api`, `web` or `postgres` containers, and never runs `make e2e-down` (that would drop nothing, but would restart the stack). Always finish a scenario with MailCatcher back up.

Fixed facts about this running stack, taken from `.env.e2e` / `docker-compose.e2e.yml` and the plan (`.agents/tasks/lifecycle-emails/issues/04-retry-sweeper-cron.plan.md`):

- Web app / API (proxied): `http://localhost:3001` — `POST /api/auth/register` registers a user and fires the inline welcome send; `POST /api/lifecycle-emails/unsubscribe` (ticket 03) unsubscribes.
- MailCatcher UI/API: `http://localhost:1081`. The `api` container reaches it as `SMTP_HOST=mailcatcher`, `SMTP_PORT=1025`. MailCatcher keeps messages **in memory**: stopping it empties the inbox, so counts restart at `0` after every `dc start mailcatcher`.
- Postgres: `postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db`. The volume persists across runs: the ledger may already hold rows from earlier e2e runs and QA sessions (S0 drains them).
- Inside the running `api` container, `LIFECYCLE_EMAILS_ENABLED=true` and `LIFECYCLE_EMAILS_UNSUBSCRIBE_SECRET=e2e-tests-unsubscribe-secret`.
- Sweeper script (plan D8): `apps/api/src/notifications/adapters/primary/retryLifecycleEmailDeliveries.script.ts`, compiled to `dist/src/notifications/adapters/primary/retryLifecycleEmailDeliveries.script.js`. No flags. It boots the app context, runs `RetryLifecycleEmailDeliveriesUseCase`, logs one summary line and closes.
- Summary line (plan, use-case test 6): `Lifecycle email retry summary: candidates=N, sent=N, failed=N, abandoned=N, skippedDisabled=N, skippedUnsubscribed=N, skippedRecipientNotFound=N, skippedAlreadyClaimed=N, errored=N`.
- Ledger statuses: `pending | sent | failed | abandoned`. New columns: `attempts` (integer, default `1`), `last_attempted_at` (timestamptz, not null).
- Constants: `STALE_PENDING_THRESHOLD_MINUTES = 15` (a `pending` row is stranded once `last_attempted_at` is more than 15 minutes old); `LIFECYCLE_EMAIL_MAX_ATTEMPTS = 5` (1 inline send + 4 retries, then `abandoned`).
- Nothing runs the sweeper automatically on this stack (there is no cron locally). It only runs when a step below runs it, so every ledger change you see comes from the step you just ran.

Commands use `curl`, `jq`, `psql`, `openssl` and `docker compose`. Run everything from the repository root, in **one shell session** (the scenarios reuse variables and functions). Define once:

```bash
DB="postgresql://postgres:e2e-tests-password@localhost:5433/benefriches_e2e_tests_db"
dc() { docker compose --env-file .env.e2e -f docker-compose.e2e.yml "$@"; }
SWEEPER=./dist/src/notifications/adapters/primary/retryLifecycleEmailDeliveries.script.js

# Run the sweeper inside the api container (same env as the running API: kill switch on, SMTP_HOST=mailcatcher).
# Prints the summary line (and any per-row error line) and the exit code; the full output goes to /tmp/sweep.log.
sweep() {
  dc exec -T "$@" api node "$SWEEPER" > /tmp/sweep.log 2>&1; local rc=$?
  grep -E 'retry summary|Retry failed' /tmp/sweep.log; echo "exit code: $rc"
}

# Simulate a mail outage / recovery.
mc_down() { dc stop mailcatcher; }
mc_up() { dc start mailcatcher && until curl -sf -o /dev/null http://localhost:1081/messages; do sleep 1; done; echo "mailcatcher up"; }

# Register a fresh user; sets USER_ID and EMAIL, prints the HTTP status.
register() {
  USER_ID=$(uuidgen | tr 'A-Z' 'a-z')
  EMAIL="qa-lifecycle04-$(date +%s)-$RANDOM@example.com"
  curl -s -o /tmp/register-response.json -w '%{http_code}\n' -X POST http://localhost:3001/api/auth/register \
    -H "Content-Type: application/json" \
    -d "{
      \"id\": \"$USER_ID\",
      \"email\": \"$EMAIL\",
      \"firstName\": \"Jean\",
      \"lastName\": \"Dupont\",
      \"structureType\": \"company\",
      \"structureActivity\": \"other\",
      \"structureName\": \"ADEME\",
      \"personalDataStorageConsented\": true,
      \"personalDataAnalyticsUseConsented\": false,
      \"personalDataCommunicationUseConsented\": false,
      \"subscribedToNewsletter\": false
    }"
}

# A user's ledger rows: id | status | attempts | seconds since last attempt | sent_at | error_message
ledger() {
  psql "$DB" -At -F ' | ' -c "SELECT id, status, attempts,
      extract(epoch FROM now() - last_attempted_at)::int,
      coalesce(sent_at::text, 'NULL'), coalesce(error_message, 'NULL')
    FROM lifecycle_email_deliveries WHERE user_id = '${1:-$USER_ID}' ORDER BY created_at;"
}

# Number of welcome emails MailCatcher holds for an address (exact subject, as in 03).
welcome_count() {
  curl -s http://localhost:1081/messages | jq --arg email "${1:-$EMAIL}" \
    '[.[] | select(.subject == "Bienvenue chez Bénéfriches" and (.recipients[] | contains($email)))] | length'
}

# What the sweeper should pick up right now: the plan's D6 predicate, written by hand.
candidates() {
  psql "$DB" -At -c "SELECT count(*) FROM lifecycle_email_deliveries d JOIN users u ON u.id = d.user_id
    WHERE u.lifecycle_emails_unsubscribed_at IS NULL AND d.email_type IN ('welcome')
      AND (d.status = 'failed' OR (d.status = 'pending' AND d.last_attempted_at < now() - interval '15 minutes'));"
}

# Unsubscribe token, as in 03 S9.
SECRET=e2e-tests-unsubscribe-secret
sign() { printf 'v1.%s.%s' "$1" "$(printf '%s' "lifecycle-emails-unsubscribe:v1:$1" | \
  openssl dgst -sha256 -hmac "$2" -binary | base64 | tr '+/' '-_' | tr -d '=')"; }
```

(`tr` lowercases the UUID, as in 03: macOS `uuidgen` prints uppercase.) `sweep` passes its arguments to `dc exec` before the service name, so `sweep -e LIFECYCLE_EMAILS_ENABLED=false` overrides the variable for that one process only (S10).

A failed inline send needs a few seconds to settle: the account-created listener inserts `pending`, the mailer fails, then the row is marked `failed`. With MailCatcher stopped, the long-running `api` process usually hits `SmtpMailer`'s 5 s connection timeout (`Connection timeout`) rather than a DNS error, so `register` itself takes ~5 s to return; a fresh sweeper process usually fails at once with `getaddrinfo ENOTFOUND mailcatcher`. After each registration done with MailCatcher down, wait ~5 s before reading the ledger.

If Docker access is not available, this guide cannot be run: simulating the outage and running the sweeper both need `docker compose`. Fall back on S16's automated tests.

## S1 — A welcome email lost to a mail outage arrives once the mail server recovers

Ticket scenario 1; ACs "retries deliveries in `failed` status", "updates the existing ledger row", "a successful retry moves the row to `sent` and records the send timestamp".

1. `mc_down`. Observe: the `mailcatcher` container is stopped (`dc ps mailcatcher` shows no running container).
2. `register`. Observe: `201` — the outage does not break signup (01 S4).
3. After ~5 s, `ledger`. Observe: exactly **one** row, `failed | 1 | <a few seconds> | NULL | <error>`, where `<error>` is non-empty (typically `Connection timeout`, or `getaddrinfo ENOTFOUND mailcatcher` / `getaddrinfo EAI_AGAIN mailcatcher`). Keep its id: `DELIVERY_ID=$(ledger | cut -d' ' -f1); ERR=$(ledger | awk -F' \\| ' '{print $6}'); echo "$DELIVERY_ID / $ERR"`.
4. `mc_up`. Observe: `mailcatcher up`; `welcome_count` prints `0` (the inbox restarted empty and nothing retried yet — the running API does not retry on its own).
5. `candidates`. Observe: `1`.
6. `sweep`. Observe:
   ```
   … Lifecycle email retry summary: candidates=1, sent=1, failed=0, abandoned=0, skippedDisabled=0, skippedUnsubscribed=0, skippedRecipientNotFound=0, skippedAlreadyClaimed=0, errored=0
   exit code: 0
   ```
7. `welcome_count`. Observe: `1`.
8. `ledger`. Observe: still exactly **one** row, with the **same id** as `$DELIVERY_ID`, now `sent | 2 | <a few seconds> | <timestamp of the sweep> | <the same error as $ERR>`. The error is kept on purpose (audit: "failed with X, then sent", plan D2 step 6). Cross-check: `psql "$DB" -At -c "SELECT sent_at >= last_attempted_at AND sent_at - last_attempted_at < interval '15 seconds' FROM lifecycle_email_deliveries WHERE id = '$DELIVERY_ID';"` → `t` (the send timestamp was recorded by this retry, right after its claim).
9. `psql "$DB" -At -c "SELECT count(*) FROM lifecycle_email_deliveries WHERE user_id = '$USER_ID';"`. Observe: `1` — the retry inserted nothing.

## S5 — A pending row written moments ago is left alone

Ticket scenario 2; AC "a `pending` row younger than the threshold is left untouched". A listener that is still sending holds a fresh `pending` row; the sweeper must not send a second copy. The in-flight state is seeded by hand (no send can be slowed down on this stack).

1. MailCatcher up. `register`. Observe: `201`; after a few seconds `welcome_count` → `1` and `ledger` → one `sent | 1` row.
2. Turn it into a send "still in flight", attempted one minute ago:
   ```bash
   psql "$DB" -c "UPDATE lifecycle_email_deliveries SET status = 'pending', sent_at = NULL, last_attempted_at = now() - interval '1 minute' WHERE user_id = '$USER_ID';"
   ```
   Observe: `UPDATE 1`. `ledger` → `pending | 1 | ~60 | NULL | NULL`.
3. `candidates`. Observe: `0`. `sweep`. Observe: `candidates=0`, `sent=0`.
4. `welcome_count` → still `1` (no second copy). `ledger` → unchanged: `pending | 1 | ~60+`, `sent_at` `NULL`.
5. Boundary: `psql "$DB" -c "UPDATE lifecycle_email_deliveries SET last_attempted_at = now() - interval '14 minutes' WHERE user_id = '$USER_ID';"`, then `sweep`. Observe: `candidates=0`; `welcome_count` → `1`; row still `pending | 1`.

   ```bash
   psql "$DB" -c "UPDATE lifecycle_email_deliveries SET created_at = now() - interval '2 days', last_attempted_at = now() - interval '5 minutes' WHERE user_id = '$USER_ID';"
   ```

## S8 — Repeated failures stop at the attempt cap and end `abandoned`

Ticket scenario 3; ACs "the number of attempts per delivery is capped" and "a delivery that has exhausted its attempts is left in a state distinguishable from one awaiting retry". Realistic path: the outage lasts through every retry.

1. `mc_down`, `register`, wait ~5 s. `ledger` → `failed | 1`. Keep `DELIVERY_ID` as in S1 step 3.
2. With MailCatcher still down, run the sweeper three times, reading the ledger after each run:
   ```bash
   for i in 1 2 3; do sweep; ledger; done
   ```
   Observe, for each run: the summary line has `failed=1` for this row (`candidates=` may be higher only if you left other failed rows behind; `sent=0`), and the row goes `failed | 2`, then `failed | 3`, then `failed | 4`, each time with the same id, a fresh `last_attempted_at` and a non-empty `error_message`.
3. Fourth retry (fifth attempt overall): `sweep; ledger`. Observe: summary `abandoned=1`, `failed=0`; row `abandoned | 5 | … | NULL | <mailer error>`.
4. `mc_up`, then `candidates` → `0`, `sweep`. Observe: `candidates=0`, `sent=0`, `abandoned=0` — the capped row is not picked up any more.
5. `welcome_count` → `0` (nothing was sent), and `psql "$DB" -At -c "SELECT count(*), max(attempts) FROM lifecycle_email_deliveries WHERE user_id = '$USER_ID';"` → `1|5`: still exactly one row, five attempts.
6. The state is distinguishable when someone reads the ledger: `psql "$DB" -c "SELECT status, count(*) FROM lifecycle_email_deliveries GROUP BY status ORDER BY status;"`. Observe: an `abandoned` line separate from `failed` (`failed` means "will be retried", `abandoned` means "gave up"). `grep -n 'abandoned\|LIFECYCLE_EMAIL_MAX_ATTEMPTS' apps/api/src/notifications/core/models/lifecycleEmail.ts` shows `"abandoned"` in `lifecycleEmailDeliveryStatusSchema` and `LIFECYCLE_EMAIL_MAX_ATTEMPTS = 5` with its rationale.
7. The capped row also blocks a genuine re-send (it stays the single row for that email): the S12 helper from 03 (`send_welcome "$USER_ID" "$EMAIL"`, defined in `docs/qa/lifecycle-emails/03.md`) prints `outcome: skipped-already-sent`, and the row count stays `1`. Optional.

Shortcut when time is short: instead of steps 1–3, take any `failed` row with MailCatcher down, `UPDATE lifecycle_email_deliveries SET attempts = 4 WHERE id = '<id>'`, run `sweep` once. Observe: `abandoned | 5`.

## S11 — A user who unsubscribed after the failure receives nothing

Ticket scenario 4; AC "the script skips deliveries for users who have since unsubscribed".

1. `mc_down`, `register`, wait ~5 s, `mc_up`. `ledger` → `failed | 1`. `candidates` → `1` (this row).
2. Unsubscribe (the email never arrived, so sign the link yourself, as in 03 S9):
   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:3001/api/lifecycle-emails/unsubscribe \
     -H "Content-Type: application/json" -d "{\"token\": \"$(sign "$USER_ID" "$SECRET")\"}"
   ```
   Observe: `204`.
3. `candidates` → `0` (the query joins `users` and skips unsubscribed users, plan D6).
4. `sweep`. Observe: `candidates=0, sent=0`.
5. `welcome_count` → `0`. `ledger` → unchanged, `failed | 1`, original error. The row stays `failed` for good; the `users.lifecycle_emails_unsubscribed_at` column explains why.
6. Run `sweep` once more. Observe: the same — the unsubscribed user's row does not churn every hour.
7. Control (proves step 4 was the unsubscribe, not something else): `psql "$DB" -c "UPDATE users SET lifecycle_emails_unsubscribed_at = NULL WHERE id = '$USER_ID';"`, `sweep`. Observe: `sent=1`, `welcome_count` → `1`.

An unsubscribe landing between the sweeper's read and its send is caught by `LifecycleEmailSender.retry()` (`skipped-unsubscribed`); that window is too small to hit by hand. Covered by the unit test "retry skips a recipient who has unsubscribed since the failure" in `apps/api/src/notifications/core/services/lifecycleEmailSender.spec.ts`.

## S12 — Two sweepers claiming the same row: only one sends

Plan D5: the claim is `UPDATE … WHERE id = ? AND status = ? AND attempts = ?`; the loser updates nothing and reports `skipped-already-claimed`. This scenario makes the race deterministic by holding the "first sweeper's" claim open in `psql` while the real sweeper runs.

1. `mc_down`, `register`, wait ~5 s, `mc_up`. `ledger` → `failed | 1`; keep `DELIVERY_ID`.
2. In the background, claim the row the way a sweeper does and keep the transaction open 30 s; then run the sweeper while the lock is held:
   ```bash
   psql "$DB" -c "BEGIN;
     UPDATE lifecycle_email_deliveries SET status = 'pending', attempts = attempts + 1, last_attempted_at = now() WHERE id = '$DELIVERY_ID';
     SELECT pg_sleep(30);
     COMMIT;" > /tmp/claim.log 2>&1 &
   sleep 1; sweep; wait
   ```
   The sweeper's candidate `SELECT` still sees the committed `failed | 1` row (a plain read does not wait for the lock); its claim `UPDATE` waits for the `psql` transaction, then re-checks its `WHERE`, finds `attempts` changed, and updates nothing. `sweep` therefore returns only after the 30 s.
3. Observe: summary `candidates=1` (for this row), `skippedAlreadyClaimed=1`, `sent=0`, `errored=0`.
4. `welcome_count` → `0` (the loser did not send). `ledger` → one row `pending | 2 | <~30>` — the winner's claim, untouched by the loser.
5. If step 3 shows `candidates=0` instead, the app context took longer than 30 s to boot and read after the commit; re-run steps 1–4 with `pg_sleep(60)`.
6. Clean-up (the "winner" never sends in this simulation): `psql "$DB" -c "UPDATE lifecycle_email_deliveries SET last_attempted_at = now() - interval '16 minutes' WHERE id = '$DELIVERY_ID';"`, `sweep`. Observe: `sent=1`, `welcome_count` → `1`, `ledger` → `sent | 3`.

## S13 — Two overlapping runs never double-send

The realistic version of S12: a slow run overlapping the next one, or a manual `scalingo run` during the cron run.

1. Create three failed deliveries:
   ```bash
   mc_down; IDS=(); EMAILS=()
   for i in 1 2 3; do register; IDS+=("$USER_ID"); EMAILS+=("$EMAIL"); done
   sleep 5; mc_up
   for id in "${IDS[@]}"; do ledger "$id"; done
   ```
